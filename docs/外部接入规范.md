# 外部软件接入规范

本文件是 `dsh-decision-engine` 对**外部软件**（游戏、业务系统、设备控制、模拟器、自定义
API）的接入契约。它只描述接口，不描述任何具体游戏的适配 —— 本插件**不为任何具体游戏做
适配**，这条边界由 `tests/unit/architecture.test.ts` 保证。

规范里出现的每个类型都对应 `src/` 中的真实定义，符号名可在源码中点对点核对。

**交付完整任务**请先读 [任务接管协议](任务接管协议.md)：主 Agent 一次给目标、计划和完成条件，
执行器直接读取和操作环境，完成后返回结果。本文保留底层单步决策与适配器契约；第 4 节的
`/decide` 是由外部程序管理循环的另一种接法，不是整任务接管入口。

---

## 0. 先选角色：你是环境，还是决策者？

```text
                    ┌──────────────────────────┐
   环境侧（你实现）  │   EnvironmentAdapter     │  观察 + 执行
                    └────────────┬─────────────┘
                                 ↓  DecisionRequest
                    ┌──────────────────────────┐
                    │     Decision Engine      │  校验 / 路由 / 归一化
                    └────────────┬─────────────┘
                                 ↓
                    ┌──────────────────────────┐
   决策侧（你实现）  │   DecisionProvider       │  在有限候选集里作答
                    └──────────────────────────┘
```

绝大多数外部软件只需要 **A. 环境侧**：

> 「我能提供结构化状态，也能执行动作；请帮我选一个。」

只有当你自己就是一个决策模型（或规则引擎）时，才需要 **B. 决策侧**。

**两边都不需要知道对方存在。** 环境侧不知道谁在决策；决策侧不知道动作怎么执行。

## 1. 共同的数据契约

### 1.1 DecisionRequest（引擎交给决策侧的东西）

```ts
interface DecisionRequest {
  objective?: string                            // 目标，自然语言
  state: string | Record<string, unknown>       // 环境状态：结构化对象或字符串
  candidates: DecisionCandidate[]               // 有限候选集（必须是有限的）
  constraints?: string[]                        // 硬约束
  mode?: 'choice' | 'ranking' | 'score' | 'classification'   // 默认 choice
  provider?: string                             // 指定 provider；不传用默认
  metadata?: Record<string, unknown>            // 环境附加上下文
}

interface DecisionCandidate {
  id: string            // 稳定 id，同一工作流里含义必须一致
  description: string   // 这个选项做什么
  metadata?: Record<string, unknown>
}
```

硬性要求：

| 规则 | 说明 |
| --- | --- |
| `id` 稳定 | 同一个工作流里重复决策时，同一个 `id` 必须指同一件事 |
| 候选有限 | ≤ 64 个；超了会被 `invalid_request` 拒绝 |
| `id` 唯一 | 重复 id 直接拒绝，不会「取第一个」 |
| 禁止自由生成 | 决策方**只能**返回候选集里已有的 `id`，返回别的会被 `unknown_candidate` 拒绝 |

### 1.2 DecisionResult（决策侧交回的东西）

```ts
interface DecisionResult {
  provider: string          // 你的 provider id
  mode: DecisionMode        // 实际执行的模式，等于请求的 mode
  selected?: string         // 选中的候选 id（单步动作只需要这个字段）
  ranking?: { id: string; score?: number }[]    // 完整偏好顺序，最优在前
  confidence?: number       // 0..1
  confidenceKind?: 'normalized' | 'provider_raw' | 'unavailable'
  latencyMs: number         // 你在内部花掉的时间
  debug?: { raw?: unknown; rawConfidence?: number; notes?: string[] }  // 仅 debug 请求时保留
}
```

### 1.3 `confidenceKind` 是**必填**的语义声明

置信度数字在不同决策方之间**不可比**。因此协议要求：**有数字就必须有 kind**。

| kind | 什么时候用 | 引擎会拿它跟 `confidenceThreshold` 比吗 |
| --- | --- | --- |
| `normalized` | 你已经把结果映射到可跨决策方比较的 0..1 尺度 | **会**。低于门限则升级 |
| `provider_raw` | 这是你自己尺度上的原始值 | 不会。只上报 |
| `unavailable` | 你这个模式给不出可比较的数值 | 不会。诚实的「没有」，不是 0 |

校验层会拒绝这四种组合（都有对应测试）：

```text
有 confidence 但没有 confidenceKind      → invalid_decision
有 confidenceKind 但没有数字             → invalid_decision
confidenceKind 是未知字符串              → invalid_decision
confidenceKind = 'unavailable' 却带数字  → invalid_decision
confidence 不在 0..1                     → invalid_decision
```

**如果你拿不准，就用 `provider_raw`。** 声明 `normalized` 等于承诺这个数字可以和别的
决策方的数字放在同一个门限下比较；做不到就如实说 `provider_raw`，引擎不会因此拒绝你的决策。

> 现实参考：Laya 自己上报 `provider_raw`，因为实测它的 entropy 置信度不反映决策质量
> （毫无信息的状态 0.039、明确决策 0.15，几乎不动）。见 `examples/laya-head-calibration.mjs`。

### 1.4 观察状态（环境侧产出）

```ts
interface Observation {
  status: 'ok' | 'insufficient' | 'unsupported' | 'error'
  source: string            // 你自己的环境 id
  state?: unknown           // status 为 ok 时才需要
  reason?: string           // 非 ok 时必填，说明为什么
  summary?: string          // 给人和模型看的一行描述
  metadata?: Record<string, unknown>   // 诊断计数，不要塞原始大对象
}
```

`insufficient` 是**一等状态**，不是错误路径。环境看不懂就必须说 `insufficient`，
引擎会升级回主 Agent。**禁止猜。**

## 2. A. 环境侧接入

### 2.0 一步到位：`dsh-decision-engine/embed`

不需要 DSH 进程、不需要 DSH 服务，也不需要自己拼装引擎/注册表/运行时。一行创建：

```js
import { createDecisionLayer, CustomEnvironmentAdapter } from 'dsh-decision-engine/embed'

const decisions = createDecisionLayer({
  laya: { modelDir: '/path/to/laya/bundle' },   // 省略则交给 SDK 自己找缓存
  confidenceThreshold: 0.55,
  runtime: { maxSteps: 10 },
})

decisions.environments.register(new CustomEnvironmentAdapter({ /* 见 2.2 */ }))

const outcome = await decisions.decideEnvironment({
  environment: 'my-system',
  objective: '把当前流程推进到成功。',
  mode: 'single-step',        // 或 'decision-only' / 'bounded-loop'
})
```

它组合的是**同一个**引擎、注册表与 provider，不是第二套实现，所以嵌入方拿到的决策契约、
升级词表、置信度规则完全一致。`decideEnvironment()` 返回的是**值**（可 JSON 序列化），
不是异常 —— 这正是跨进程桥需要的形状：

```js
{ status: 'needs_escalation', environment: 'blind', steps: 0,
  escalation: { status: 'needs_escalation', reason: 'insufficient_observation',
                environment: 'blind', guidance: '…', details: { … } } }
```

`createDecisionLayer` 的选项：

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `laya` | `true` | `false` 关闭；或直接传 Laya 配置对象（`modelDir`、`device`、`autoLoad`、`idleTtlMs`…） |
| `providers` | `[]` | 额外 provider；第一个注册的会成为默认 |
| `defaultProvider` | 第一个已注册 | 未知 id 会立刻报错，而不是等到第一次决策 |
| `runtime` | 插件默认 | `maxSteps` / `maxDurationMs` / `noProgressLimit` / `repeatedDecisionLimit` … |
| `confidenceThreshold` | `0.55` | 只对 `confidenceKind: 'normalized'` 生效 |
| `timeoutMs` | `30000` | 单次决策的 provider 预算 |
| `telemetryLimit` | `200` | 内存中保留的遥测条数 |

方法：`decide(request)`（失败**抛** `DecisionError`，带 `code`）、
`decideEnvironment({...})`（运行失败**返回**升级值）、`runTask({...})`（整任务执行）、`environments`、`providers`、`runtime`、
`telemetry()`、`health()`、`dispose()`。

**如果出现 `insufficient` 却不打算处理，就不要调用 `decideEnvironment` 的循环模式** ——
升级是设计行为，不是需要重试的故障。

> 这一节就是「只优化接口」的产物：原先外部接入方要从 4 个子路径 import 并手动注册 3 次，
> 现在是一次调用。`examples/verify-embedding.mjs` 在**完全没有 DSH 包**的情况下验证了它
> （12 项检查，含跨边界的置信度规则与「升级是值不是异常」）。

### 2.1 契约（`embed` 之下的一层）

```ts
interface EnvironmentAdapter {
  readonly id: string
  readonly source: string
  observe(input?: { signal?: AbortSignal; timeoutMs?: number }): Promise<Observation>
  buildDecisionRequest(observation: Observation, objective: Objective): DecisionRequest | Promise<DecisionRequest>
  mapDecision(result: DecisionResult, observation: Observation): EnvironmentAction | Promise<EnvironmentAction>
  execute(action: EnvironmentAction, input?: { signal?: AbortSignal; allowRisky?: boolean }): Promise<ActionResult>
  isDone?(observation: Observation, objective: Objective): boolean | Promise<boolean>
  dispose?(): Promise<void> | void
}
```

| 方法 | 你的责任 | 硬性要求 |
| --- | --- | --- |
| `observe` | 读你的结构化状态 | **不要抛错**，返回非 `ok` 的 `Observation` |
| `buildDecisionRequest` | 把你的状态变成有限候选集 | 候选必须**全部可执行** —— 这不是建议，见 2.3 |
| `mapDecision` | 候选 id → 你的具体动作 | 只映射你自己提供过的 id；越界要抛 `unknown_candidate` |
| `execute` | 执行动作 | 观察 `signal`；返回 `{ ok, message?, done? }` |
| `isDone` | 目标是否已达成 | 可选。返回 `true` 会立刻结束循环 |

### 2.2 最省事的做法：用 `CustomEnvironmentAdapter`

你不需要自己实现上面那 5 个方法，只要提供回调：

```ts
import { CustomEnvironmentAdapter } from 'dsh-decision-engine/environments/custom'

const adapter = new CustomEnvironmentAdapter<MyState>({
  id: 'my-system',                      // 环境 id，注册后用它路由
  observe: () => mySystem.snapshot(),   // 返回结构化状态；返回 undefined = 「现在读不到」
  candidates: state => [
    { id: 'continue', description: '继续', action: { op: 'continue' } },
    { id: 'retry',    description: '重试', action: { op: 'retry' } },
    { id: 'abort',    description: '放弃', action: { op: 'abort' } },
  ],
  execute: (candidate) => mySystem.apply(candidate.action.op),
  isDone: state => state.status === 'success',
  summarize: state => `status=${state.status} progress=${state.progress}`,
  defaultObjective: '把当前流程推进到成功。',
  projectState: state => ({ status: state.status, progress: state.progress }),  // 决定模型看到什么
})
```

各回调的语义：

| 回调 | 签名 | 说明 |
| --- | --- | --- |
| `observe` | `() => State \| undefined` | 返回 `undefined` ⇒ `insufficient`（不猜）；抛错 ⇒ `error` |
| `candidates` | `State => Candidate[]` | 一个候选可以带 `available(state)` 谓词，为 `false` 时不出现在候选集里 |
| `execute` | `(candidate, input) => { ok, message?, state?, done? }` | `done: true` 会结束循环 |
| `isDone` | `(state, objective) => boolean` | 可选，在**执行前**也会检查一次（目标已达成就不动作） |
| `projectState` | `State => unknown` | 可选，决定送进决策请求的状态长什么样（可以只暴露必要字段） |
| `summarize` | `State => string` | 可选，一行描述，便于日志与升级时人对齐 |
| `defaultObjective` | `string` | 可选，调用方没给 objective 时用 |

候选里 `risky: true` 的动作，在没有显式 `allowRisky: true` 时运行时**拒绝执行**并升级。

### 2.3 `mapDecision` 必须是全函数（重要）

引擎只保证：**决策方选出来的 id 一定在你的候选集里**（否则 `unknown_candidate`）。
它**不保证**那个 id 此刻仍然可执行。所以：

- 候选 id 与「具体要执行什么」必须在**你提供候选的那一刻**就绑定好，
  最省事的做法就是像 2.2 那样把 `action` 直接挂在候选上；
- `execute` 时要重新校验前置条件，不可执行就返回 `{ ok: false, message }`，
  运行时会把 `action_execution_failed` 升级回主 Agent；
- **不要**在 `mapDecision` 里现查「这个字符串是什么意思」—— 那是把动作语义交给模型。

### 2.3b 并发：一个适配器同时被两个调用方驱动

同一个运行时按环境 id 排他执行任务；任务未结束或超时后的调用未排空时，第二次执行会被
`environment_unavailable` 拒绝。`CustomEnvironmentAdapter` 的候选与原始观察绑定，避免把
较早的模型结果映射到后来状态的同名动作。直接驱动适配器时仍要自行协调对实际环境的访问。

两条出路，按你的场景选：

```js
// ① 并发 HTTP 服务：每个请求一个适配器实例（最清楚）
async function handleRequest(state) {
  const adapter = makeAdapterForThisRequest(state)   // 每次新建，绑定这次快照
  return decisions.decideEnvironment({ environment: adapter, objective: '…' })
}

// ② 共享一个适配器：用 decision()，它按实例串行化整段流程
const { result, action } = await adapter.decision(
  (request) => decisions.decide(request),
  { description: '…' },
)
```

`decision()` 把四个协议步骤绑在一起并**按实例排队**，所以共享适配器不会互相冲掉候选表；
不同适配器之间仍然并行。适配器另外保留最近几次候选集（有界），并且**动作自带它由哪个
候选映射而来**，因此 `mapDecision` 之后即使又发生了新的观察，`execute` 也会执行
**当初那个**候选，而不是按 id 去猜当前状态里的同名项。

> 这两条都是真实接入方（laya-router 改造）踩出来的，已写进测试
> `tests/unit/integrator-protocol.test.ts`。

### 2.4 注册

进程内（你自己就是 Node 侧代码，例如本地服务、CLI、模拟器）：

```ts
ctx.decisionEngine.environments.register(adapter)
// 之后用环境 id 驱动：
await ctx.decisionEngine.run({ environment: 'my-system', objective: { description: '…' }, mode: 'single-step' })
```

## 3. B. 决策侧接入

### 3.1 契约

```ts
interface DecisionProvider {
  readonly id: string
  readonly capabilities: readonly ('choice' | 'ranking' | 'score' | 'classification')[]
  decide(request: DecisionRequest, context?: DecisionContext): Promise<DecisionResult>
  healthCheck?(): Promise<ProviderHealth>
  dispose?(): Promise<void> | void
}
```

| 项 | 要求 |
| --- | --- |
| `id` | 稳定、小写，注册后不可与别的 provider 重名（重名会报错，除非显式 replace） |
| `capabilities` | **如实申报**。请求了你不支持的模式会被引擎在你之前拒绝（`provider_unsupported_capability`）。`noul` 这类私有概念**不能**作为 capability |
| `decide` | 返回值会被归一化：越界 id 报 `unknown_candidate`，未知排序项被丢弃，`selected` 与 `ranking` 互补派生 |
| `provider`（返回值里） | **可以**从你的返回值里指定，用来点名真正作答的那条臂。不填则引擎填注册时的 id |
| `healthCheck` | 可选。抛错会被当作 `unavailable`，不会影响别的 provider |
| `context.signal` | 请观察它。引擎本身用竞速保证调用方一定超时返回，但你自己的清理要靠它 |

### 3.1b 复合 Provider：让「哪条臂答的」可见

一个 provider 内部可能有好几条臂（先用模型、失败退本地规则）。引擎注册的是**一个** id，
但你可以在返回值里用 `provider` 点名真正作答的那条臂：

```ts
async decide(request) {
  try {
    const answer = await this.#model.decide(request)
    return { ...answer, provider: 'laya' }        // 这条臂答的
  } catch {
    return { ...this.#rules.decide(request), provider: 'rules' }
  }
}
```

引擎**不会**用注册 id 覆盖它 —— 否则复合 provider 无法从结果里分辨是哪条臂答的。
这个字段只是描述性的（路由已经发生过了）。

### 3.1c Token / 用量是协议的一部分

不要在 provider 私有统计里数 token 再让调用方去掏 —— `DecisionResult.usage` 就是给这个的：

```ts
return {
  provider: this.id,
  mode: request.mode ?? 'choice',
  selected,
  ranking,
  confidence: 0.7,
  confidenceKind: 'provider_raw',
  usage: { inputTokens: 225, outputTokens: 2 },   // 可选
  latencyMs: Date.now() - started,
}
```

`usage.inputTokens` 会进入 telemetry 的 `inputTokens` 字段。非有限数或负数会被**丢弃**
（不影响决策成功）。语言模型之外的 provider 可以用 `usage.metrics` 放自己的计数。

> 设计理由：每个接入方最后都要给模型调用记账。协议里没有这个字段时，接入方只能去掏
> provider 的内部统计（`runtime.stats.inputTokens`），那正是 provider 边界要防的耦合。

### 3.2 最小实现

```ts
import type { DecisionProvider, DecisionRequest, DecisionResult } from 'dsh-decision-engine/core'

class MyProvider implements DecisionProvider {
  readonly id = 'my-provider'
  readonly capabilities = ['choice'] as const

  async decide(request: DecisionRequest): Promise<DecisionResult> {
    const started = Date.now()
    const picked = await myModel.choose(request.state, request.candidates)
    return {
      provider: this.id,
      mode: request.mode ?? 'choice',
      selected: picked,
      ranking: request.candidates.map((c, i) => ({ id: c.id, score: 1 - i / request.candidates.length })),
      confidence: 0.7,
      confidenceKind: 'provider_raw',   // 见 1.3 —— 拿不准就用这个
      latencyMs: Date.now() - started,
    }
  }
}
```

注册与路由：

```ts
ctx.decisionEngine.providers.register(new MyProvider(), { enabled: true })
// 之后：请求里传 provider: 'my-provider'，或把 defaultProvider 配成它
```

### 3.3 你不能做的事

```text
✗ 返回候选集以外的 id                  → unknown_candidate
✗ 输出 tool call / 具体动作（"browser_click"）  → 层级泄漏，本插件内部有静态测试禁止 provider 知道工具名
✗ 把 noul 之类私有概念当成 capability    → registration 被拒
✗ 让上游依赖 debug.raw                  → 它只在请求 debug 时返回，不属于协议
```

## 4. 单步决策服务（HTTP，由外部程序管理循环）

当外部程序希望自己管理执行循环时，可以把「请求决策」做成一次 HTTP 调用，动作仍在环境
进程里执行。如果希望主 Agent 交付一次任务后完全退出中间循环，请使用
[任务接管协议](任务接管协议.md) 的 `decision_run` / `runTask` 和环境 `state` / `action`
接口；这两种 HTTP 接法的请求方向和循环归属不同。

### 4.1 线格式

决策引擎本身不提供 HTTP 服务；转接由你的服务做，形状建议如下。

**请求**

```http
POST /api/decide
Content-Type: application/json

{
  "objective": "把当前流程推进到成功。",
  "state": { "step": "review", "healthy": true },
  "candidates": [
    { "id": "continue", "description": "继续" },
    { "id": "retry",    "description": "重试" },
    { "id": "abort",    "description": "放弃" }
  ],
  "mode": "choice",
  "provider": "laya"
}
```

**成功响应（200）**

```json
{
  "status": "decided",
  "provider": "laya",
  "mode": "choice",
  "selected": "continue",
  "ranking": [{ "id": "continue", "score": 0.55 }, { "id": "retry", "score": 0.3 }, { "id": "abort", "score": 0.15 }],
  "confidence": 0.09,
  "confidenceKind": "provider_raw",
  "latencyMs": 184
}
```

**升级响应（200，非错误）**

```json
{
  "status": "needs_escalation",
  "reason": "low_confidence",
  "provider": "laya",
  "lastDecision": { "selected": "continue", "confidence": 0.09, "confidenceKind": "normalized" },
  "guidance": "让用户或主 Agent 决定这一步；模型置信度不足。",
  "details": { "message": "…" }
}
```

**为什么升级也用 200**：这不是传输失败，而是**业务结果**。用 4xx/5xx 会让调用方把
「模型不确定」和「服务挂了」混在一起。建议只在参数非法时用 400。

### 4.2 状态码约定

| 码 | 含义 | 调用方该做什么 |
| --- | --- | --- |
| `200` + `status: decided/executed/done` | 决策成功 | 按 `selected` 执行你的动作 |
| `200` + `status: needs_escalation` | 决策层拒绝继续 | 读 `reason` / `guidance`，交回主 Agent 或问用户；**不要重试同一个请求期待不同结果** |
| `400` | 请求非法（候选为空、id 重复、state 缺失、mode 未知） | 修请求 |
| `503` | provider 不可用（例如模型未加载） | 可退避重试；`reason` 会说明 |

### 4.3 从 Node 转接（示例骨架）

```js
import http from 'node:http'

// 决策引擎在你的进程内可用时，直接调用它 —— 不必绕 HTTP。
const server = http.createServer(async (req, res) => {
  if (req.url !== '/api/decide' || req.method !== 'POST') return res.writeHead(404).end()
  const body = JSON.parse(await readBody(req))
  try {
    const result = await decisions.decide({
      objective: body.objective,
      state: body.state,
      candidates: body.candidates,
      mode: body.mode,
      provider: body.provider,
    })
    res.writeHead(200, { 'content-type': 'application/json' }).end(JSON.stringify({
      status: 'decided',
      provider: result.provider,
      mode: result.mode,
      selected: result.selected,
      ranking: result.ranking,
      confidence: result.confidence,
      confidenceKind: result.confidenceKind,
      latencyMs: result.latencyMs,
    }))
  } catch (error) {
    // 决策层的一切拒绝都是带 code 的：把它映射成你的响应，不要吞掉。
    res.writeHead(200, { 'content-type': 'application/json' }).end(JSON.stringify({
      status: 'needs_escalation',
      reason: error.code ?? 'internal',
      guidance: error.message,
    }))
  }
})
```

`error.code` 的取值就是第 5 节列出的那套词表。

### 4.4 游戏场景的完整回路

```text
游戏进程（浏览器 / 引擎）
  │  ① 读自己的结构化状态（禁止截图理解）
  │  ② 由状态生成有限候选集，并把「候选 → 动作」的映射留在本地
  ↓  POST /api/decide  { objective, state, candidates, mode }
你的本地服务（Node）
  ↓  decisions.decide(...)        ← 本插件在这里
  ↑  { selected, confidence, confidenceKind, … }
  ↑  HTTP 200
游戏进程
  │  ③ 用本地映射把 selected 换成真实动作并执行
  │  ④ 重新读状态；不变化就交给主 Agent
  ↓
```

要点：**游戏侧从不 import 本插件，插件也从不 import 游戏**。中间只有这一份线格式。
`gitproject/laya-router` 就是按这个形状改造的参考实现（它的 `/api/decide` 由
`CustomEnvironmentAdapter` + `LayaDecisionProvider` 支撑，游戏端只发状态、只收动作）。

## 4.5 跨入口捕获错误：不要用 `instanceof`

本包是**逐入口打包**的，所以 `lib/core/index.js` 与 `lib/plugin.js` 各自带一份
`DecisionError` 类定义 —— `a instanceof B` 会得到 **false**，即使两边抛的是同一种错误。
真实接入方就踩过这个坑，把 `no_candidates` 静默降级成了 `internal`。

两种可靠写法：

```js
import { isDecisionError } from 'dsh-decision-engine/core'

try { await decisions.decide(request) }
catch (error) {
  if (isDecisionError(error)) handle(error.code)      // ① 结构化判断，跨副本成立
  else if (typeof error?.code === 'string') handle(error.code)  // ② 直接读 code，最省事
  else throw error
}
```

`DecisionError` 现在带一个 `brand` 字段（实例与静态都有），并且实现了
`Symbol.hasInstance`，所以**同一个包内**的 `instanceof` 仍然正确；跨入口/跨副本请用
`isDecisionError()` 或直接读 `error.code`。`error.brand` 会随 `toJSON()` 之外的自然属性
保留，桥接层重建对象时带上 `name: 'DecisionError'` 与 `code` 也能被识别。

## 5. 错误与升级词表

外部软件应当原样转发或映射这套 `code`，不要自造同义词：

```text
provider_unknown                 provider_unavailable
provider_unsupported_capability  invalid_decision
unknown_candidate                low_confidence
provider_timeout                 provider_failed
insufficient_observation         environment_unsupported
environment_unknown              environment_unavailable
no_candidates                    invalid_request
action_mapping_failed            action_execution_failed
no_progress                      repeated_decision
budget_exhausted                 aborted
needs_vision                     needs_planning
high_risk_action                 internal
```

其中**必须由主 Agent 接管**的（即「不要重试」）：`insufficient_observation`、
`environment_unsupported`、`needs_vision`、`needs_planning`、`high_risk_action`、
`no_progress`、`repeated_decision`、`budget_exhausted`、`low_confidence`。

## 6. 一致性检查清单

接入方交付前逐条自查：

```text
[ ] 候选 id 稳定，且同一工作流里含义不变
[ ] 候选数量有限，且每个候选都能真的执行
[ ] observe 不抛错，读不到就说 insufficient（绝不猜）
[ ] 有 confidence 就一定带 confidenceKind；拿不准用 provider_raw
[ ] execute 重新校验前置条件，失败返回 ok:false 而不是抛异常
[ ] 观察 signal / 超时；不要自己写无限重试
[ ] 高风险动作标 risky: true，不指望引擎替你判断风险
[ ] 不把私有概念（模型名、问句类型）写进 capability 或候选 id
[ ] 不依赖 debug.raw —— 它默认不返回
[ ] 环境侧不认识任何 provider；决策侧不认识任何工具名或元素索引
```
