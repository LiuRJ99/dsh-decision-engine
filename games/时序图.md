# games/ 时序与流程

三张图：一次接管任务的**全景时序**、一次策略动作的**内部流程**、**三个驱动方**的关系。
全部按当前代码的真实行为画（端点名、`isDone`、`revision` 校验都对得上）。

---

## 图一：全景时序（一次 `decision_run` 接管）

关键点：**主 Agent 只在两头出现**——开头发一次任务，结尾验收。中间每个动作的
"观察 → 决策 → 执行"全由执行器自己转，中间不回来问。

```mermaid
sequenceDiagram
    autonumber
    participant M as 主 Agent（我）
    participant X as decision_run 执行器
    participant P as Laya provider<br/>（ONNX，宿主进程内）
    participant B as 桥 server.mjs<br/>（node，持权威局面）
    participant G as core/*.js<br/>（纯函数，与页面同一份）
    participant W as 页面<br/>（浏览器，只渲染）

    M->>X: 一次调用：objective + plan（完成条件 done=true）
    Note over X: 中间步骤主 Agent 不参与

    loop 每个动作（直到环境报 done）
        X->>B: GET /state
        B->>G: snakeLayaState() / snakeStrategyCriteria()
        G-->>B: 结构化局面 + 4 个策略候选
        B-->>X: { protocol, state, candidates[4], done:false }
        X->>P: DecisionRequest(objective, state, candidates)
        P->>P: 一次 ONNX 前向（≈200ms）
        P-->>X: selected=strategy:chase, ranking, confidence(provider_raw)
        X->>B: POST /action { candidateId:"strategy:chase" }
        B->>B: 校验 revision（过期即 409 拒绝）
        B->>G: snakeStrategyAction × 8 → snakeStep × 8
        G-->>B: 新局面
        B-->>X: { ok:true, message, observation }
        X->>X: 读 observation.done（环境自己判定终局）
    end

    X-->>M: status=done, result={score,steps,length,cause}
    M->>M: 验收最终结果

    par 同一时间，页面只是镜像（不参与决策）
        W->>B: GET /render 每 150ms
        B-->>W: 原始局面 + 奖励 + 最近落子 + 决策粒度
        W->>W: 画 canvas / 更新面板
    and 人类按键走同一条动作入口
        W->>B: POST /action { candidateId:"dir:up" }
        B-->>W: { ok:true, message, observation }
    end
```

**为什么 `loop` 里不写 `execute: "loop"`**：HTTP 环境自带 `isDone`
（`observation.done === true` → `stopReason: "The environment reports a terminal result."`），
执行器自己就会循环。钻取模式是给"环境说不出自己做完了没有"的场合用的。

## 图二：一次策略动作的内部流程

一个动作 = **模型做一个决定**（四选一）+ **本地执行一段**（蛇连走 8 步 / 方块算一个落点）。
这是整个设计里最关键的一处：模型负责决策，确定性代码负责执行。

```mermaid
flowchart TD
    A["执行器 POST /action<br/>candidateId = strategy:chase"] --> V{"revision 与当前一致？"}
    V -->|"否（有人抢先动过）"| REJ["409 拒绝<br/>「动作基于 0，当前是 1」<br/>适配器报 action_execution_failed"]
    V -->|是| PRE{"id 前缀是哪种？"}

    PRE -->|"strategy: —— 决策层发的"| ST["取策略名<br/>校验在 SNAKE_STRATEGIES / TETRIS_STRATEGIES 里"]
    PRE -->|"dir: / drop: —— 页面发的"| MV["只走一格 / 只落一个方块"]

    ST --> Q{"蛇还是方块？"}
    Q -->|蛇| LOOP["循环 N=8 次：<br/>snakeStrategyAction(state, strategy)<br/>→ snakeStep(state, action)"]
    Q -->|方块| PLACE["tetrisStrategyPlacement(state, strategy)<br/>→ tetrisApplyPlacement（一次落子）"]

    LOOP --> D{"中途死了？"}
    D -->|是| DIE["记 cause，本局结束"]
    D -->|否| OK["revision += 1"]
    PLACE --> OK
    MV --> OK
    DIE --> OK

    OK --> SNAP["返回 { ok, message, observation }<br/>observation 里已含新局面与 done"]
    SNAP --> NEXT["下次 GET /state 重新算局面与候选"]
```

**注意 `revision` 那道闸**：它挡的是"两个驱动方同时动作"——
决策层观察到局面 N、想了 200ms 再动作时，如果人在这期间按键把局面推到 N+1，
决策层的那个动作就被拒，而不是静默落到已经变了的盘面上。

## 图三：三个驱动方与它们各自的动作类型

```mermaid
flowchart LR
    subgraph DRIVERS["三个可以驱动局面的人"]
        direction TB
        D1["① 决策层<br/>decision_run / decision_decide"]
        D2["② 人类<br/>方向键 / WASD / ←→↑↓ 空格 P"]
        D3["③ 本地启发式自动<br/>页面上的查看按钮"]
    end

    D1 -->|"strategy:chase 等<br/>4 个候选"| EP
    D2 -->|"dir:up / drop:2,5"| EP
    D3 -->|"dir:* / drop:*"| EP

    EP["POST /action<br/>（唯一入口）"] --> RV{"revision 校验"}
    RV -->|通过| EX["桥执行并推进局面"]
    RV -->|过期| NO["409 拒绝"]

    EX --> ST[("权威局面<br/>只存在于桥进程")]
    ST -->|"GET /state"| D1
    ST -->|"GET /render 每 150ms"| VIEW["页面渲染<br/>canvas + 面板"]

    NOTE["决策层看到的是策略；<br/>后两个方看到的是逐步动作。<br/>三者共用同一个入口，所以谁在动、动得对不对，<br/>页面上都看得见。"] -.-> EP
```

**三条边界的实际含义：**

| 边界 | 怎么保证的 |
| --- | --- |
| 页面不持状态 | 页面只有 `view`（最近一次 `/render` 的快照），没有任何 `state` 变量 |
| 环境侧不知道 provider | 桥只发候选 id 与局面，**拿不到也拿不到概率/置信度**（接入规范要求如此） |
| 同时只应有一个驱动方 | 桥的 `revision` 守卫只保证"不静默落到过期局面上"；它**不做互斥**——同时驱动仍会互相插队 |

最后一条是已知局限，写在 README 的「局限」里。
