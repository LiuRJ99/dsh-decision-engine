# games/ — 决策层玩游戏（真实页面 + 桥持状态）

把贪吃蛇和俄罗斯方块接到 `dsh-decision-engine` 上，让**决策层在真实页面上玩**。

这是本仓库里第一个 **`status: done`** 的接管任务：终局由环境自己判定（`isDone`），
不是靠步数预算硬停。刷题那个页面做不到这件事 —— 这也是为什么游戏才是这层的主场。

## 架构：谁持状态

```text
       主 Agent 的执行器                     浏览器（真实页面）
   decision_run(endpoint=…)              snake.html / tetris.html
            │                                  │
            │ GET /state   读局面+候选          │ GET  /render  每 150ms 读画面
            │ POST /action 落子                 │ POST /action  人类按键 / 本地自动
            ▼                                  ▼
   ┌────────────────────────────────────────────────────────┐
   │  games/bridge/server.mjs                               │
   │  · 持有**权威游戏状态**（core/ 的纯函数在这里演算）        │
   │  · 把状态翻成 dsh-environment/v1 快照                    │
   │  · 同时服务真实页面与静态资源                             │
   └────────────────────────────────────────────────────────┘
```

**页面不持状态。** 权威局面只存在于桥进程里；页面只做两件事：把局面画出来，
把你的输入发回去。这样决策循环的节奏不会被前端渲染干扰，页面也不参与任何决策。

## 用的是哪一套接入方式

`docs/外部接入规范.md` 里有**两种** HTTP 接法，本目录用的是**第二种**：

| 规范章节 | 谁的循环 | 端点 | 用途 |
| --- | --- | --- | --- |
| 4.1 / 4.4 | **游戏进程**自己管循环，向外请求决策 | `POST /api/decide` | laya-router 原来的形状（本目录刻意不用） |
| **任务接管协议** | **主 Agent 的执行器**管循环 | `GET /state` + `POST /action` | `decision_run` 的 `endpoint` |

规范第 9–11 行明确写了：*"交付完整任务请先读任务接管协议……本文第 4 节的 `/decide` 是由外部程序
管理循环的另一种接法，不是整任务接管入口。"* 桥走的是任务接管这一条。

## 跑起来

```bash
# 贪吃蛇
node games/bridge/server.mjs --game snake  --port 8787 --seed 7
# 俄罗斯方块
node games/bridge/server.mjs --game tetris --port 8788 --seed 11
```

浏览器打开 `http://127.0.0.1:8787/snake.html` 看局面；让决策层玩（**注意 objective 里要说明"你只选策略"**）：

```jsonc
{
  "endpoint": "http://127.0.0.1:8787/",
  "objective": "完整地玩一局贪吃蛇。你每次只做一个决定：选择接下来一段时间里蛇要执行的策略（追食物/保活/贴尾巴/直走）。选定后蛇会按该策略连续走若干步，然后你再选一次。目标是尽量吃到食物、活得越久越好。一直玩到蛇死亡、本局结束为止。",
  "plan": [
    { "id": "play",
      "objective": "每次读局面与四个策略的说明，选一个最合适的：能追到食物就选 chase；食物不可达或空间紧张时选 survive；需要留退路时选 hug。",
      "completion": { "path": "done", "equals": true } }
  ]
}
```

方块同理，objective 换成"为当前方块选择一种落点策略（消行/补洞/平整/压低）"。

**不需要 `execute: "loop"`** —— HTTP 环境自带 `isDone`，执行器自己循环，撞到终局就停。

**objective 要写清"你只负责选策略"**：桥给的候选只有 4 个策略，如果目标里写"选下一步往哪走"，
模型会去猜一个不存在的动作。第一版桥正是因为目标与候选不匹配而空转烧预算。

## 协议端点

| 端点 | 用途 |
| --- | --- |
| `GET /state` | `dsh-environment/v1` 快照：**结构化局面 + 4 个策略候选** + `done` + `result`（给 `decision_run`） |
| `POST /action` | 执行动作，返回 `{ ok, message, observation }`。接受 `strategy:*`（决策层）与 `dir:*`/`drop:*`（页面） |
| `GET /render` | 给页面用的画面：原始局面 + 奖励 + 最近落子 + 候选 + 计数 + 决策粒度 |
| `POST /reset` | 换一局（`{ seed, difficulty }`） |
| `GET /health` | 桥自检 |
| `/`、`/snake.html`、`/js/*`、`/style.css` | 真实页面与本地游戏核心 |

## 动作 id（接入规范 1.1：同一工作流里 id 必须稳定且唯一）

**决策层只会看到 `strategy:*`** —— 那是桥给它的候选集：

| 谁发的 | 编码 | 例子 |
| --- | --- | --- |
| **决策层（唯一候选）** | `strategy:<名>` | `strategy:chase` / `strategy:survive` / `strategy:hug` / `strategy:straight`（蛇）<br>`strategy:lines` / `strategy:holes` / `strategy:flat` / `strategy:low`（方块） |
| 页面的人类按键 / 本地自动 | `dir:<方向>` | `dir:up` / `dir:down` / `dir:left` / `dir:right` |
| 同上 | `drop:<旋转>,<列>` | `drop:2,5` / `drop:1,-1` |

后两类**不会出现在候选集里**，是页面自己发的（给人玩、或本地自动对照用）。桥两种都接受。

候选的 `description` **必须用 core 自带的措辞**，不要自己另写一版：

| 游戏 | 候选描述来自 | 例子 |
| --- | --- | --- |
| snake | `snakeStrategyCriteria()` | `go for the food: the only strategy that earns reward (+10 per food) — the food is 1 steps away` / `play it safe: earns no reward, but avoids the -100 game-over penalty (390 cells reachable from the head)` |
| tetris | `tetrisStrategyCriteria()` | `clear rows with this piece: choose the landing that removes the most complete rows now (+100 per row)` / `avoid covering empty cells: …` |

状态同理，**用 `snakeLayaState()` / `tetrisLayaState()`**，不要自己拼：

```jsonc
// snake：7×7 局部视野（H=头 o=身 F=食物 #=障碍）+ 相对食物偏移
{ "grid": "20x20", "view": [".......",".......",".#.....",".ooH...","...F...",".......","......."],
  "heading": "right", "length": 3, "food_offset": {"dx":0,"dy":1}, "food_distance": 1,
  "free_cells_from_head": 390, "distance_to_own_tail": 3, "blocked_obstacle_cells": 8 }
// tetris：裁剪过的堆叠行 + 每列高度 + 空洞数
{ "board_rows_from_top": 19, "stack": ["#....#....","##...###..", ...],
  "column_heights": [19,18,7,10,15,19,18,18,16,10], "holes": 14,
  "current_piece": "T", "current_rotation": 0, "next_piece": "L", "lines_cleared": 5 }
```

**为什么这件事必须写死成规矩**：这两个函数是游戏侧专为这个模型准备的输入分布，旧的 laya-router
就喂这个。第一版桥图省事自己写了"中文散文 + 绝对坐标"，实测**明显更差**（见下表）。
桥传给决策层的 `state` 是**对象**，provider 的 `serializeState()` 会自己 `JSON.stringify`。

## 实测结果

### 输入格式的影响（同一种子，只改格式）

| 游戏 | 中文散文 + 绝对坐标 | core 的 `*-layaState` + 英文措辞 |
| --- | --- | --- |
| 贪吃蛇 | 8 步 / 0 分 / 撞障碍 | **16 步** / 0 分 / 撞障碍 |
| 俄罗斯方块 | 18 块 / 1 行 / **100 分** | 33 块 / 5 行 / **600 分** |

格式改对后两边都变好：蛇存活翻倍，方块分数 6 倍。**这说明"给模型喂什么格式"是这套东西里
一等重要的变量，不是细节。**

### 为什么决策粒度是"策略"（三组对照的结论）

桥**只给决策层一种候选：策略**（蛇 4 选 1 / 方块 4 选 1），具体怎么走由本地算法算。
这不是拍脑袋定的，是同一个种子跑三组对照跑出来的：

| 粒度 | 模型负责什么 | 本地代码负责什么 |
| --- | --- | --- |
| 逐步 | **每一步**选方向 / 选落点 | 什么都不做，忠实执行 |
| 逐步 + 否决 | 同上 | 安全否决：会立刻死 / 会自陷的选择被驳回，改走启发式 |
| **策略（采用）** | 每 N 步选一次**策略** | 按策略算出每一步怎么走（`snakeStrategyAction` / `tetrisStrategyPlacement`） |

**🐍 贪吃蛇（种子 7，普通难度）**

| 粒度 | 得分 | 步数 | 长度 | 结局 |
| --- | --- | --- | --- | --- |
| 逐步 | **0** | 16 | 3 | 撞障碍物死亡 |
| 逐步 + 否决 | **1** | 300 | 4 | **没死**，跑满 300 步预算 |
| **策略** | **12** | 166 | 15 | 撞墙死亡（场地已收缩到 81 格障碍） |

中间那组只否决了 **16 次（5%）**，却把"第 16 步就死"变成"300 步不死"：**模型的走法在两次
致命错之间是可用的，否决层负责不让那一次错把整局终结**。但它 300 步只吃到 1 个食物 —— 活着，不挣分。

**🧱 俄罗斯方块（种子 11，普通难度）**

| 粒度 | 得分 | 消行 | 方块数 | 结局 |
| --- | --- | --- | --- | --- |
| 逐步 | **600** | 5 | 33 | 顶死（20 个洞） |
| 逐步 + 否决 | **600** | 5 | 36 | 顶死（否决只触发 1 次 —— 它只在"会立刻顶死"时拦，拦不住慢慢挖洞） |
| **策略** | **55400** | **95** | 200 | **没死**，跑满预算，盘面只剩 1 个洞 |

### 结论：分数是"决策粒度"挣的

- 让模型**每一步**自己选 → 蛇 0 分、方块 600 分
- 让模型**只选策略**、本地算具体走法 → 蛇 12 分、方块 **55400 分**

旧 laya-router 报的"蛇 4–6 分、方块 13–15 行 / 1700–2400 分"，形状上就是"策略"这一档。
**所以那个"很客观的得分"主要来自"策略粒度 + 本地执行"，而不是逐步决策的能力。**

这不是说 provider 没用：策略档里"选哪个策略"仍然是模型做的，而且做得不差。
**它的能力边界是"粗粒度四选一"，不是"细粒度逐步决策"** —— 这正好对上它的设计定位
（System-1 决策模型：从有限选项里选一个）。**所以桥固定用策略粒度：模型负责它擅长的决策，
本地代码负责执行。**

那两组逐步/否决的实现已经删掉了（`games/` 当时还没进版本控制，所以没留在历史里）。
要复跑对照得重新加回来 —— 结论和数字都记在上面，不值得为它保留三倍的代码路径。

### 逐步决策为什么那么差

上面"逐步"那一列的难看数字，原因是查清了的，**主要不在模型**。旧 laya-router 的"好成绩"
靠的是三层，而第一版桥只保留了第三层：

| 旧系统的三层 | 结论 |
| --- | --- |
| ① **否决层**：会立刻死 / 自己没把握（top-1 概率低于门槛）/ 会自陷 → 否决并改用本地启发式 | 前两条实现过、测过；第三条做不了（见下）。最终**不再保留** —— 它只对"逐步决策"有意义 |
| ② **决策粒度**：模型每 4–8 步选一次**策略**，具体走法由本地算法执行 | **成绩提升主要来自这里** —— 但见下面对"谁在决策"的更正 |
| ③ **输入格式**：`snakeLayaState()` + 英文候选措辞 | 已修复（蛇存活翻倍、方块分数 6 倍） |

**逐步决策失败的证据**（留下的实测记录）：候选描述里白纸黑字写着
`DEATH — dies at once (hits the wall)`，另有两条写着 `SAFE`，模型仍然选了那条 `DEATH` 的，
排名第 3 / 3。**不是信息不足，是它没在用信息。**

模型的位置偏置也是实测过的（早前 8 道选择题的对照实验：正序倒序各问一遍，
选中的**槽位**几乎不动 13/16 压在第一位，而选中的**内容**跟着选项翻转）。
`provider_raw` 的置信度不跟随决策质量，不能拿来当判据。

同样的信息在**策略粒度**下就够用了 —— 那时模型要做的只是"四选一"，而它做得不差。
**这也是选策略粒度的真正理由：把那句"读懂局面挑最优"换成模型真正擅长的"在少数选项里选一个"。**

### 关于 `low-top-probability`（旧否决层的第三条）

它是一道"模型到底在不在区分"的闸：门槛 = `1.2 / 候选数`，如果模型给首选答案的分数没比
均匀分布高多少，就判定它在瞎猜，改用本地启发式。（除以候选数是因为 Laya 的 choice 分数是
"1 − 归一化熵"，选项一多天然就低。）

**这条在本架构里做不了，而且不该在环境侧做：**

- 协议的动作请求只带候选 id，**不带概率或置信度** —— 桥看不到那个数字；
- 这不只是"没实现"：接入规范第 605 行明写 *"环境侧不认识任何 provider"*，**环境侧本来就该看不到**；
- 正确的家是 **provider 层**：规范 §3.1b 的**复合 Provider**（没把握时改由规则臂作答，
  并用返回值里的 `provider` 点名是哪条臂答的），或者把置信度标定成 `normalized` 后
  交给引擎的 `confidenceThreshold` 门限。

#### 实测：这道闸本身也不成立

**顺手测了一下"如果恢复它会不会有用"——结论是它测的不是模型把不把握，而是选项的排列顺序。**

策略模式（4 个候选，floor = 1.2/4 = 0.3），连采 8 次：

```text
第1次 top-1=0.551 ✓   第2次 0.542 ✓   第3次 0.642 ✓   第4次 0.406 ✓
第5次 top-1=0.438 ✓   第6次 0.615 ✓   第7次 0.568 ✓   第8次 0.483 ✓
→ 8 次全部高于门槛（0 次触发）；8 次全部选中 strategy:chase —— 而 chase 正是候选列表的第一个
```

于是做了对照：**同一个局面、同样四个选项，只把顺序倒过来。**

| | 喂进去的顺序 | 返回的排名 | 选中 |
| --- | --- | --- | --- |
| 正序 | `chase, survive, hug, straight` | chase=**0.551** > survive=0.184 > hug=0.143 > straight=0.123 | chase（槽位 1） |
| 倒序 | `straight, hug, survive, chase` | straight=**0.295** > hug=0.260 > survive=0.241 > chase=0.204 | straight（槽位 1） |

两件事同时被证伪：

1. **分数严格按位置递减**，赢家跟着顺序翻转 —— 模型没在读选项文本，它锁第一个槽位。
   倒序那一栏里，食物就在一步之遥（`chase` 写着"唯一能拿奖励的，食物还剩 1 步"），
   而它选了 `straight`（写着"不拿奖励"）—— 内容上荒谬，位置上必然。
2. **换个顺序就能把 top-1 从 0.551 压到 0.295，正好跨过 0.3 的门槛。**
   同一局面、同一组选项，闸门却从"放行"变成"否决" —— 它量的是排列，不是把握。

这个数字从两个源头来：`ranking[0].score` 就是模型概率（`rankingFromProbabilities` 直接用
`probabilities[id]` 当 score），而 `confidence` 是熵派生值（实测 0.06–0.25，不跟随质量）。
两者都被排列顺序主导。

#### 对成绩解读的影响（重要）

策略模式跑出的好成绩（蛇 12 分 / 方块 55400 分）**不能记在"模型会选策略"头上**：
它每次都是取第一个列出的策略。之所以结果不差，是因为
`SNAKE_STRATEGIES = ["chase", …]`、`TETRIS_STRATEGIES = ["lines", …]` 的**第一个恰好是个合理默认**
（追食物 / 消行）。**在"挑策略"这件事上，它目前等价于一个常量函数。**

这不影响协议、桥、本地执行那几层（它们是实测通过的），但确实改变了对"谁在决策"的判断。
要让它真的在选，得先解决位置偏置本身（换 provider，或做标定/微调）。


## 页面数据层的改造

三个页面都保留了原有的**全部 UI 与玩法**，改的只是"局面从哪来、动作谁执行"：

| 原来 | 现在 |
| --- | --- |
| `let state = createSnakeState(...)` / `createTetrisState(...)` 页面持状态 | 从 `GET /render` 同步局面 |
| `tick()` / 重力循环自己推进 | 只渲染，不推进 |
| `refreshStrategy()` / `decideForNpc()` 调 `askDecide()` | **删除** —— 这是 laya 注入式实现 |
| `snakeHeuristicAction` / `tetrisHeuristicPlacement` 作为 NPC 决策 | 降级为"本地启发式自动"这个**查看用**按钮 |
| 人类模式本地改状态（`snakeStep` / `tetrisMove` / `tetrisHardDrop`） | 按键 → `POST /action`（`dir:*` / `drop:*`） |
| 决策面板画概率条 / nook / stackDanger / router 门槛 | 改画**决策层真实输出**：候选集、选中项、排名、候选数 |
| `autotest` / `mock` / `pieces` 查询参数 | 移除（改由桥驱动） |
| `renderHealthBadge` 查 `/api/health` | 直接查桥的 `/health` |
| 标题与文案里的 `laya-router` | 改为本项目 |

**保留未动**：计分器（奖励分解）、浏览器记录（localStorage）、难度档、节奏滑块、
棋盘显隐（含 localStorage 记忆）、下一块预览、落点半透明预览、大厅与游戏间跳转、
全部键盘操作（蛇：方向键/WASD/空格暂停；方块：←→移动、↑旋转、↓软降、空格落子、P 暂停）。

方块页的一个设计取舍：原来左右/旋转是**直接改盘面**的，而桥的落子是**原子**的。
所以前四个键改的是**本地预览落点**（半透明预览跟着动），空格才把落点发回桥执行。
按键语义一个没少，只是"什么时候真正落子"变得明确了。

## 验证状态

全部**实机验证通过**（浏览器打开、看到真实数据、按键真实生效）：

## 踩过的坑（都是实测撞出来的）

1. **别自己发明喂给模型的状态/候选格式。** 第一版桥图省事写了"中文散文 + 绝对坐标"，
   而 core 里现成有 `snakeLayaState()` / `tetrisLayaState()` / `snakeMoveCriteria()`
   —— 那是游戏侧专为这个模型准备的输入分布。改回官方格式后：**蛇存活 8 → 16 步，
   方块 100 → 600 分**。这条是影响最大的一个坑。
2. **落点 id 不能有歧义。** 最初用 `rot1-x-1`，而列号可以是负数，于是 `x-1` 既可能是"列 1"
   也可能是"列 -1"，运行时直接报 `无法解析落点 "rot1-x-1"`。改成 `drop:<rot>,<x>`。
3. **候选 id 要带命名空间。** 接入规范 1.1 要求 id 在同一工作流里稳定唯一；裸的
   `up/down/left/right` 会跟别的 id 空间撞车，改成 `dir:` / `drop:` 前缀。
4. **候选排序别写反。** 第一版按 `aggHeight` 降序排，把"空洞最多、堆最高"的落点排到了最前面。
   代价函数要跟游戏目标同向：少空洞、堆得低、表面平整。
5. **`next` 字段可能是对象也可能是字符串。** 直接拼进状态文本会得到 `[object Object]`。
6. **core 的事实字段名要对着源码核，不能凭印象。** 实际是 `eats` / `distAfter` / `spaceAfter`
   （不是 `eatsFood` / `distanceToFood` / `freeSpace`），`cleared` / `aggHeight`（不是 `linesCleared` /
   `aggregateHeight`），`gridFloodFill` 返回的是数字（不是 Set）。
7. **`renderRecords` / `sessionLesson` 的签名是对象参 / game 参**，不是想当然的位置参。

## 迁移说明：跟 laya-router 的关系

`games/core/` 与页面是从 `laya-router/public/` 复制过来的，复制而非引用，因为两者目标已分叉：

| | laya-router | 本仓库 |
| --- | --- | --- |
| 决策从哪来 | 自己的服务端 `/api/decide`（路由器 + Laya 对比） | `dsh-decision-engine` 的 provider |
| 页面角色 | 提问者（`askDecide`） | 纯渲染 + 输入回传 |
| 循环归属 | 游戏页面 | 主 Agent 的执行器 |
| 耦合点 | `js/npc-client.js` | 已丢弃 |

**没有带过来的**：`src/**`（laya 服务端、`src/decision/plans/*.mjs` 那套路由决策）、
`public/js/npc-client.js`（耦合点）。游戏规则（core）本身不依赖 laya，也不依赖 DOM。

## 局限

- 桥一次只持一局；`POST /reset` 可以换一局（换 seed/难度）。
- 页面是轮询 `/render`（150ms），不是推送。够顺滑，也够简单。
- **同一时刻只应有一个驱动方**：决策层（`decision_run`）和页面的动作都打到同一个
  `POST /action`，同时进行会互相插队。桥对 `revision` 有校验，但不做互斥。
- 决策水平受 provider 限制，跟桥无关。要提升只能换 provider —— 这是设计使然，不是桥的缺陷。
